# Loop: Implement and Verify

## 使う場面

- 機能追加・refactorが複数ファイルにまたがる
- テスト・lint・typecheck・buildで成否を判定できる
- 1〜3回の自律的な修復サイクルで品質が上がる

## 契約

### Goal
要求された振る舞いだけを、最小の一貫した変更で実装する。

### 着手前
1. 受け入れ基準を内部で言い直す。
2. 影響ファイルと既存の規約を特定する。
3. 編集前に検証コマンドを決める。
4. rollback境界（どこまで戻せばよいか）を決める。

### 反復
1. 最小の動く変更を入れる。
2. 最も安価で関係の深い検証から実行する。
3. 失敗の証拠を記録する。
4. コードを再び変える前に根本原因を診断する。
5. 診断した原因に関係するコードだけを変更する。
6. 失敗した検証を再実行し、必要なら範囲を広げる。

### 予算
- 最大反復: 3
- 同一根本原因: 2
- full suite実行: ユーザーが明示しない限り最大1回
- 明確な利点がない限りGraph / Subagentへ昇格しない

### 停止: 成功
必要な受け入れ基準と選んだ検証が全て通ったら止める。

### 停止: エスカレーション
次のいずれかで止めて報告する。
- 同じ根本原因が新しい根拠なしに2回続いた
- 外部のcredentialやサービスが必要になった
- 変更が明示された安全境界を越える
- タスクの前提がリポジトリの実態と矛盾する
- 反復予算を使い切った

### 最終報告
- 何を変えたか
- 実行した検証
- 残る不確実性
- 注意すべきリスク
