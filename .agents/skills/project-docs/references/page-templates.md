# ページの雛形

どのページも、1 行目の見出しのあとに確認日と、このページで扱う範囲・関連ページへのリンクを書く。
見出しは `## 1. 〇〇` のように番号を振ると、ほかのページから `#1-〇〇` でリンクできる（生成スクリプトのアンカーは GitHub と同じ規則）。

## 仕様.md

```markdown
# 仕様

確認日: YYYY-MM-DD

<このプロダクトは何か、を 1〜2 文で>。
処理の流れは [<処理の流れ>](../02_アーキテクチャ/<処理の流れ>.md)、構成は [システム構成](../02_アーキテクチャ/システム構成.md) にある。

## 1. 目的
## 2. できること          使い方 × 入力 × 出力の表
## 3. 出力の形式          保存するファイル・API のレスポンスなど
## 4. 制約                外部サービスの上限、対応しないもの。推定値は根拠と日付を添える
## 5. やらないこと
## 6. 技術スタック        項目 × 採用したものの表
```

## システム構成.md

```markdown
# システム構成

確認日: YYYY-MM-DD

## 1. モジュール          ファイル × 役割の表。外部 I/O をどこに寄せているか
## 2. データの流れ        テキストの図（または Mermaid。HTML で描画しないならテキスト）
## 3. 外部サービス        相手 × 使う場面 × 認証
## 4. 動く場所            ローカル / サーバー、待ち受けるアドレス
```

## <処理の流れ>.md（PJ の中心になるページ）

```markdown
# <処理の流れ>

確認日: YYYY-MM-DD

<何を入力に、何を決めて、何を出力するまでか>。コードの正本は `<path>` の `<関数>` である。

## 1. 全体の流れ          分岐の図
## 2〜. 分岐ごとの詳細     条件と選び方
## n. 失敗したとき         失敗の種類 × 再試行 / 切り替え / この件だけ失敗 / 全体を止める の表
## n. 引き継ぐ状態         処理をまたいで持ち越す状態、きっかけ、変化、使う関数
## n. 止める条件
```

## 設計判断の記録.md

```markdown
# 設計判断の記録

確認日: YYYY-MM-DD

新しい判断は末尾に足す。判断を変えたときは、古い ADR を消さずに状態を「置き換え」にして、新しい ADR へのリンクを書く。

## ADR-001 <判断を一文で>

- 状態: 採用 / 置き換え（ADR-00x） / 廃止
- 背景: 何に困っていたか。制約
- 判断: 何を選んだか（選ばなかった案も短く）
- 結果: 良くなること、引き受けること
```

## 初期セットアップ.md

```markdown
# 初期セットアップ

確認日: YYYY-MM-DD

設定項目の一覧は `.env.example` が正本である。

## 1. 必要なもの
## 2. 依存を入れる        `make setup` などの入口と、使わない場合の手順
## 3. 外部サービスの準備   ログイン・キーの発行。秘密値は変数名だけを書く
## 4. 環境変数            変数 × 用途 × 既定
## 5. 動作を確かめる      テストと、副作用のない確認コマンド
```

## トラブル対処.md

```markdown
# トラブル対処

確認日: YYYY-MM-DD

## 1. <状況を一言で>

（実際に出るメッセージをコードブロックで）

何が起きているか。どうするか（自動で回復するなら、何もしなくてよいと書く）。
```

## 検証記録（07_検証記録/YYYY-MM-DD_題名.md）

```markdown
# YYYY-MM-DD <題名>

## 目的
## 条件                  データ・設定・バージョン
## 結果                  数値は表で
## 分かったこと
## 次にやること          仕様や ADR に反映したら、そのリンク
```
