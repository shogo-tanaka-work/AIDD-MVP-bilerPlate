# Plan Interview

書き始める前に問う。計画の弱点はコードを書いてから見つけるより、質問で見つける方が安い。

## 発動タイミング

- `docs/SPEC.md` や機能仕様を書く前
- 複数ファイルにまたがる変更の計画を提示する前
- ユーザーの依頼が「何を作るか」は明確でも「どこまで作るか」「何をしないか」が曖昧なとき
- 設計案に対して「これで抜けはないか」と聞かれたとき

typo修正や1ファイルの明確な変更には使わない。

## 進め方

1. 依頼を1〜2文で言い直し、ユーザーに確認する。
2. 下の観点から、**答えが計画を変える質問だけ**を選ぶ。1回に出す質問は3〜5個まで。
3. 回答を受けて、確定した前提・未確定の前提・スコープ外を分けて書く。
4. 残る未確定が計画を変えなくなったら止め、計画（対象・変更方針・検証方法）を提示する。
5. 答えが得られない前提は、採用した既定値と理由を明記して進める。

質問は「はい/いいえ」や選択肢で答えられる形にし、ユーザーが即答できないものは「後で決める」を選べるようにする。

## 問う観点

### 目的と成功条件
- この変更で誰の、どの行動が変わるか
- 完了したと判断する観測可能な条件は何か
- 今回やらないことは何か（v2以降、手動対応、対象外）

### 境界と入力
- 入力はどこから来るか（UI、API、ファイル、外部サービス）。信頼できるか
- 空・上限・不正値・重複・同時実行のとき何が起きるべきか
- 既存データや既存ユーザーへの影響はあるか（migration、互換性）

### 失敗経路
- 外部依存が落ちたとき、遅いとき、部分的に失敗したときどう振る舞うか
- 途中で失敗した処理はやり直せるか。二重実行は安全か
- 利用者に見せるエラーと、運用者が追う情報は何か

### 非機能
- 想定する規模（件数、頻度、同時利用）と、それを超えたときの許容
- 認証・認可の境界はどこか。誰が何を見てよいか
- 秘密値・個人情報を扱うか。どこに保存し、ログに出さないか

### 設計判断
- 既存のパターン・utility・型で解けないか
- 新しい依存や抽象化は本当に必要か
- 後から変えにくい判断（DB schema、公開API、URL）はどれか。`docs/ARCH.md` に残すべきか

### 検証
- どのテスト・型検査・lint・buildで成否を判定するか
- 実ブラウザや実環境で確認が必要な導線はどれか

## 出力形式

```markdown
## 言い直し
（依頼の要約）

## 確定した前提
- ...

## 未確定の前提と採用する既定値
- （前提）→ 既定値: ... / 理由: ...

## スコープ外
- ...

## 計画
- 対象: ...
- 変更方針: ...
- 検証方法: ...
```

## アンチパターン

- 観点表を上から順に全部聞く（答えが計画を変えない質問は出さない）
- 質問を投げたまま、回答を待たずに実装を始める
- 「後で決める」と言われた前提を、決まったものとして実装する
- 面接の結果を口頭で済ませ、`docs/SPEC.md` や計画に反映しない
